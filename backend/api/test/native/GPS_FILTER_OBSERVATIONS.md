# Native GPS filter observation contract

Run `NODE_ENV=production LOG_LEVEL=fatal node --test backend/api/test/native/kalmanFilter.node.mjs` with Node24 and Pino10.3.1 in the backend dependency environment. The focused Linux workflow isolates dependencies and does not boot the API, databases, GPS receiver or vehicle controls. Native tests exercise the actual filter and geofence evaluator; no numerical operation is mocked.

`KalmanFilter2D` retains its scalar position smoothing algorithm and displacement-derived angular velocity estimate. It is **not a full state/velocity covariance Kalman model**, map matcher, calibrated navigation filter or geodesic motion model. Local P/R variances use metres squared, process Q metres squared per second; converting both variances to an angular axis cancels in the dimensionless gain. Ground speed retains the approximate111320metres-per-degree conversion and longitude cosine. This approximation is not a pole-accurate tracking claim.

Every starting/update observation must have finite geographic coordinates, nonnegative integer milliseconds in the native Date range, and accuracy0–1,000,000metres. Configuration honors positive measurement variance and nonnegative process noise (including zero), bounded at1e12. Measurement variance is max(configured floor, accuracy²/4), so low-accuracy/default behavior is explicit. Readable legacy fields remain, but are read-only; returned receipts are separately owned. Use `init` for an explicit admitted reset.

Observation time must increase. An exact duplicate coordinate/time/accuracy returns the previous receipt without reducing uncertainty or changing velocity; conflicting duplicates and backward observations throw. Longitude innovations and displacement take the shortest arc across the dateline. Antipodal or >=180degree predicted travel is ambiguous and throws rather than inventing a direction. Complete candidate geographic/covariance/finite admission precedes one private state publication; rejected observations cannot poison subsequent valid outputs.

Very uneven cadence may expose instability in the preserved scalar predictor. An inadmissible candidate is rejected with the entire prior receipt retained; applications must deliberately reinitialize rather than receive a fabricated finite trajectory. This change does not claim a new physical tracking model, distributed stream ordering, persistence acknowledgment or rollback of other ingestion side effects. The current ingestion service calls the filter before geofence/Redis construction; the focused suite does not bootstrap that whole service or assert database delivery.

The independent oracle uses precision-weighted scalar updates for100-point trajectories at five noise policies. Separate native cases cover millisecond timing, real dateline geometry/geofence behavior, zero process noise, configured measurement floor, initial/reset rejection, temporal replay and returned-state ownership.
