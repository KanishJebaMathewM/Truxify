# Confirmed federated server-round recovery

The existing round owner now prepares one bounded, versioned encrypted receipt for the current server round: native architecture and model weights, selected clients, complete accepted contribution arrays, completion and clipping/noise policy. It uses the existing Fernet keyring; key initialization/rotation and aggregation mathematics are unchanged. A private native Keras serving candidate and complete owned publication fields are prepared before the atomic Redis compare-and-set. The original input containers cannot change the encoded receipt during native preparation. Successful publication replaces the server model object; callers must refresh server.model references.

The canonical key federated:server_snapshot:v1 has no cache TTL. It contains only the latest round, with at most64 selected IDs of256UTF8 bytes each and a16MiB encrypted payload ceiling. Legacy round/accepted/completion keys are best-effort compatibility mirrors, not authority. H5 checkpoints and updated-model notices are derived outcomes, reported separately from confirmed completion. A failure there does not undo or falsely reject an already confirmed round.

A coordinator restart validates and reconstructs the complete receipt while Redis survives. Remaining clients can complete a partly acknowledged round; completed models are restored with matching native predictions. A stale writer cannot overwrite a newer expected receipt. A lost write reply is reconciled by reading the actual receipt; if both reply and readback are unavailable, no success/readiness is assumed and the last confirmed native state remains intact until reconciliation. Warm reads normally expose the last confirmed local generation, rather than promising cross-coordinator read synchronization.

## Migration boundary

Legacy identity-only rounds do not contain the missing contribution arrays or unambiguous complete provenance. They are refused explicitly instead of inventing weights or automatically deleting/resetting state. Deployment into a namespace with such live legacy state requires an operator-approved migration/restart plan and backups. This PR does not execute that operation. A malformed/missing confirmed receipt also blocks readiness. Version1 supports the current native Dense/Dropout architecture semantics; topology changes need a new supported migration rather than shape-only reuse.

## Limits

Redis must preserve the confirmed key; this is not Redis power-loss/AOF/replication durability certification or multi-coordinator scheduling/consensus. Compare-and-set detects conflicts but does not elect a round coordinator. The existing unacknowledged transport GETDEL handoff, Pub/Sub delivery/lifecycle, registrations, key history and historical H5 retention are not redesigned. No unacknowledged update-delivery, notice delivery, RNG replay, server optimizer history, arbitrary callbacks/external state mutation, fatal device/process recovery or formal differential-privacy guarantee. The server's supported role aggregates serving weights; local client fitting remains unchanged. No providers, physical driver telemetry, deployment or accuracy claim.

## Native verification

Real TensorFlow/Keras, Fernet and private port-zero Redis exercise restart after clientA, remainingB completion, complete native inference continuity, policy restoration, native ACL/EVAL refusal, post-EVAL reply loss, readback loss/reconciliation, stale writers, owned input containers, incompatible same-shaped architecture, malformed/oversized receipts, explicit legacy refusal and native derived-filesystem failure. Existing model admission, failed candidate preservation, median, round-tag/replay and client HTTP controls remain. The old mocked three-client store now uses the existing native Redis fixture; its model/round assertions are retained. No numerical model/optimizer/aggregation substitutions or deselections. Existing protobuf/Keras/AnyIO deprecations remain explicit.
